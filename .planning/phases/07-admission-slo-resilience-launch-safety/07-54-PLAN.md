<revision_note>
Code inspection corrected the former plan's authority model. `ContextVmFundingAdapter` currently requires `admissionReference` for every `start_session`; `MeteredGenerationService.execute` routes affordability failure through `ContinuationService.pauseForFunding`; and the continuation contracts/SQL bind that row to a `sessionId`, accepted admission, live lease, cap hold, and worker-style checkpoint. `PgFundingTransaction.prepareMeteredAction` also creates `metered_sessions` and provider/action rows. Those are post-admission authorities, so they cannot represent a click made before admission. This plan creates a separate pre-admission service and table and leaves the existing live-worker continuation path unchanged.
</revision_note>

<interfaces>
- Add an explicit signed `start_session` arguments variant `{ mode: "pre_admission", idempotencyKey, maximum, idea }`. The adapter injects the verified owner and can dispatch it only through an injected `PreAdmissionSessionService`; no injection means unavailable/fail closed in production composition.
- A pre-admission save validates the same idea bounds/risk rules and requires `maximum >= activeProfileCeiling`. When settled spendable balance is below that maximum it writes one encrypted pending action and safe projection. It creates no funded admission, capacity reservation, cap hold, metered session/action, provider claim, worker request, workspace, or artifact version.
- If the pre-admission request races with a credit and the balance is already sufficient, return a safe `funded_admission_required` result without persisting a pending action or creating effects; the browser then follows the ordinary signed funded-admission/start path.
- The dedicated `development_pending_actions` schema is owner/idempotency/fingerprint/checkpoint/version/expiry/state/envelope metadata and one-time resume binding. It has no foreign key to `metered_sessions` or `session_cap_holds` and no plaintext idea, provider/payment credential, checkpoint key, or decrypted command projection.
- The pending-action envelope is distinct from the worker workspace envelope. Its authenticated header binds schema/kind, checkpoint ID/version, owner, command fingerprint, expiry, policy/profile/price-card/toolchain and root-manifest pins, and ciphertext digest; its encrypted body contains only the exact validated start command needed after restart. The development key is server-only, restart-stable under `.local`, never generated afresh when ciphertext already exists, and never returned through ContextVM/status/logs.
- After top-up, the browser first sends a normal signed `funded_admission` using the original maximum. Only an accepted result may supply `admissionReference` to a second signed `resume_session` command: `{ kind: "pending_action", checkpointId, expectedCheckpointVersion: 1, expectedSessionVersion: 0, idempotencyKey, approvePendingAction: true, admissionReference, pendingAction: { reference, fingerprint, kind: "start_session", maximum } }`.
- Pending-action resume validates owner, expiry, checkpoint/header/ciphertext integrity, exact command fingerprint, maximum, expected session/artifact versions at zero, current policy/profile/price-card/toolchain/root-manifest pins, and the accepted admission's same owner/cap. It atomically binds that admission plus resume fingerprint/idempotency once before effect dispatch.
- Factor the normal funded start path in `MeteredGenerationService` so pending-action resume supplies the decrypted original command plus bound admission while retaining the original command idempotency, deterministic operation ID, provider claim/lookup, SQL metering, and Plan 56 worker/verifier/artifact/preview flow. A crash/replay observes those exact durable identities and cannot create replacement work.
- Plan 56 owns worker affordability semantics: spendable funds equal free balance plus that admission's remaining held cap, while required-cap sufficiency is checked separately. This plan changes none of that code; its integration test must prove the new resume consumes its own accepted hold without a false low-balance pause.
- Extend `session_status` with the exact owner-scoped query variant `{ kind: "pending_action", checkpointId }` without inventing a session. The projection may expose type, reference, fingerprint, maximum, shortfall, expiry, state, versions, and next action; it never exposes idea/ciphertext/key/admission internals.
- Keep `createFundedCore` and every production composition unchanged; only `src/dev/dev-composition.ts` opts into the optional facade, so the production default remains fail closed.
- Legacy `ContinuationService.resumeSession` worker checkpoint commands, live-worker grace behavior, and post-grace workspace restore remain byte-for-byte compatible and covered by their existing tests.
- A revision still targets one verified Plan 56 parent artifact, uses Plan 53's metered proposal path, and commits an immutable successor only after the actual Plan 56 verifier/repository succeeds.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| Signed pre-admission command -> encrypted pending-action store | User intent becomes durable before admission and must create no execution authority. |
| Funding/admission -> explicit pending-action resume | Credited funds and a cap hold exist before the user separately consents to execute. |
| Pending-action ciphertext -> ordinary metered generation | Stored untrusted input may trigger paid/code execution only after complete owner/integrity/pin/version validation. |
| Prior artifact/revision -> successor | Cross-version data and ownership enter a new model/build action. |

## STRIDE Threat Register (ASVS L1; block on high)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-07DEV54-01 | Tampering | Pending-action envelope | high | mitigate | Dedicated AEAD envelope with canonical authenticated header, ciphertext digest, restart-stable server key, exact pin/version validation, and tamper tests. |
| T-07DEV54-02 | Elevation of privilege | Pre-admission save/resume | high | mitigate | Verified owner injection, optional dev-only facade, accepted same-owner admission binding, explicit resume, and no pre-resume provider/worker/session authority. |
| T-07DEV54-03 | Repudiation | Admission/resume/provider/charge binding | high | mitigate | Durable separate fingerprints/idempotency identities, one-time SQL claim, original operation/provider lookup, immutable ledger/version records, and crash injection. |
| T-07DEV54-04 | Information disclosure | Encrypted command and local key | high | mitigate | No plaintext command/credentials in SQL/wire/logs; `.local` server-only key material; safe allowlisted status projection and secret scans. |
| T-07DEV54-05 | Denial of service | Saved action replay | medium | mitigate | Bounded input, 30-day expiry, unique owner/idempotency constraints, transactional claim, and deterministic terminal projection. |
| T-07DEV54-SC | Tampering | policy/toolchain/root manifests | high | mitigate | No new package intake; bind and revalidate current price/profile/policy/toolchain/root-manifest identities before resume. |
</threat_model>
