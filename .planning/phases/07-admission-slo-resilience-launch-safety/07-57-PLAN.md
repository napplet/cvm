<revision_note>
The authority investigation is the controlling evidence for this split. Existing `start_session` requires an admission reference; `MeteredGenerationService.execute` currently calls the session/admission-bound `ContinuationService.pauseForFunding`; continuation SQL represents an accepted session, live lease, cap hold, and worker checkpoint; and `prepareMeteredAction` creates session/provider/action records. The new pre-admission path therefore receives its own table, encrypted envelope, store contract, and service. It does not reuse or widen the legacy continuation rows.
</revision_note>

<interfaces>
- `PreAdmissionSessionService.saveStart` receives a transport-neutral owner plus `{ idempotencyKey, maximum, idea }`, validates the ordinary start bounds/risk and active profile ceiling, and reads actual account spendability. Below the requested maximum it saves one pending action; if balance is already sufficient it returns `funded_admission_required` without saving state or creating effects.
- `development_pending_actions` stores owner/idempotency/fingerprint/checkpoint/version/expiry/state/envelope metadata plus one-time resume/admission bindings. It has no foreign key to `metered_sessions` or `session_cap_holds` and stores no plaintext idea, provider/payment credential, checkpoint key, or decrypted command.
- The pending-action envelope is a distinct schema from the worker workspace envelope. Its authenticated header binds schema/kind, checkpoint ID/version, owner, command fingerprint, expiry, expected session/artifact versions at zero, policy/profile/price-card/toolchain/root-manifest pins, key ID, and ciphertext digest. Its encrypted body contains only the validated original start command needed after restart.
- `LocalCheckpointStore` keeps ciphertext and a server-only restart-stable development key under `.local`. Existing ciphertext with missing/mismatched key fails closed; no key/ciphertext/plaintext crosses public status, diagnostics, or logs.
- Resume input is `{ kind: "pending_action", checkpointId, expectedCheckpointVersion: 1, expectedSessionVersion: 0, idempotencyKey, approvePendingAction: true, admissionReference, pendingAction: { reference, fingerprint, kind: "start_session", maximum } }` plus an owner injected by the caller.
- Resume validates owner, expiry, header/ciphertext integrity, command fingerprint, unchanged maximum, zero session/artifact versions, current pins, and a same-owner accepted admission whose held cap covers the original maximum. It commits the admission/resume fingerprint/idempotency binding once before any provider/worker effect.
- Factor the normal funded start path in `MeteredGenerationService` so the restored command plus bound admission retains the original start idempotency, deterministic operation/provider request IDs, provider lookup, charge fence, Plan 53 proposal, and Plan 56 worker/verifier/artifact behavior. Replay after a crash observes those same records and cannot issue replacement work.
- Plan 56 remains the owner of affordability after a hold: spendable equals free balance plus the action's own remaining cap, with a separate required-cap check. This plan proves that behavior through its actual-SQL handoff test and does not reimplement it.
- `ContinuationService`, its live-worker automatic wake/grace behavior, and post-grace workspace checkpoint resume stay unchanged. A pending action never claims a session, workspace, lease, or artifact checkpoint.
</interfaces>
</context>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| Validated command -> encrypted pending-action store | User intent becomes durable before any admission or execution authority exists. |
| Accepted admission -> one-time resume binding | A cap hold becomes authority for exactly one saved owner/command tuple. |
| Pending-action ciphertext -> metered generation | Restored untrusted input may trigger paid/code execution only after integrity, ownership, version, pin, and admission checks. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-07DEV57-01 | Tampering | Pending-action envelope | high | mitigate | Canonical AEAD header binding, ciphertext digest, restart-stable key, exact pin/version checks, and mutation tests. |
| T-07DEV57-02 | Elevation of privilege | Admission/resume binding | high | mitigate | Owner-scoped accepted admission lookup, exact maximum/fingerprint approval, SERIALIZABLE one-time claim, and no pre-binding effects. |
| T-07DEV57-03 | Repudiation | Original operation replay | high | mitigate | Separate durable command/resume identities, deterministic original operation/provider IDs, lookup-only recovery, and fault injection. |
| T-07DEV57-04 | Information disclosure | Command ciphertext/local key | high | mitigate | Server-only `.local` key, no plaintext SQL/wire/log projection, restrictive persistence, and secret scans. |
