# Container startup and CI

The service's missing configuration error was hidden by its uppercase-only
diagnostic filter. The fixed public mount message is now allowed explicitly;
arbitrary exception text and secret values remain redacted. Four regression
tests cover that boundary.

The control images used the normal service entrypoint but omitted its imported
infrastructure modules, nested preview packages, Docker CLI and host Chromium.
Both control targets now package these pinned dependencies, install browser
libraries for their own distribution, and check the service's `/health` route.
The offline image probe loads the actual service, verifies pinned assets, builds
the workspace, loads Paja and launches Chromium with no network, a read-only
root, dropped capabilities and the original unprivileged user.

Local validation:

- Service selection with `NAPPLET_CVM_TEST_EXTERNAL_EFFECTS=deny` and
  `NAPPLET_RUN_POSTGRES_ISOLATION=1`: 50 passed, 255 assertions, including real
  PostgreSQL migration tests.
- TypeScript 5.9.3 and `git diff --check`: passed.
- Actual `bun scripts/production.ts` without configuration: exit 1 and
  `SERVICE_MOUNT_UNAVAILABLE:/etc/napplet-cvm/service.json`.
- Later Docker builds and durability integration tests encountered host disk
  exhaustion (350 MiB available) and Docker filesystem I/O errors. Those local
  attempts are not successful image or durability evidence.

Hosted validation is available on [PR #114](https://github.com/napplet/cvm/pull/114).
The service workflow builds and boots the normal image and builds its gVisor
engine. The durability workflow runs real PostgreSQL cases and the offline
runtime/boot probes against both control image targets. The goal requires
successful current PR checks; this local record does not substitute for them.

Scope is startup, packaging and their checks. No deployment, default-branch
change, or pricing/admission implementation is part of this fix.
