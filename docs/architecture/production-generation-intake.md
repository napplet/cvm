# Protected funded generation intake

[Proposal and technical compatibility decision](https://github.com/napplet/cvm/issues/69) cover this internal recovery boundary. Public tools, original event records and saved checkpoints are unchanged.

The SDK verifies an inbound request before the production transport sees it. For validated funded `start_session` and `revise_session` calls, the transport encrypts that verified envelope and commits a recovery companion alongside its original event claim in one serializable transaction. A rollback leaves neither record; a lost commit acknowledgement leaves both available to a fresh controller. Initial handling starts immediately after that commit. The private poll recovers interrupted originals and does not queue initial admissions.

The original journal row retains its existing pending/completed format. Its companion has version `protected-contextvm-generation-intake-v1`, the owner/event/original canonical identity, an execution-context digest, payload digest, key reference and thirty-day retention deadline. A random AES-GCM data key encrypts the verified envelope and is wrapped under the mounted checkpoint KEK. Both encryption layers authenticate the stable header. Raw ideas, request parameters and key bytes are absent from the cleartext journal metadata.

Recovery first checks the actual original record and identity, then decrypts and validates the envelope, owner and payload. It recomputes the original canonical invocation identity before entering the same private adapter handler. The production context digest binds the processor contract, server policy/protocol, candidate/configuration and captured profile/card/FX material. A changed context remains unresolved; this executor does not invent a replacement policy, quote or consent. After funded action preparation, the independent [original-command executor](./production-generation-recovery.md) handles original-priced receipt/source/build/settlement recovery across supported changes.

Before interrupted intake can create fresh paid work, a concrete production authority checks the verified owner, accepted admission, active cap hold, original capacity lease expiry and the original provider's readiness observation. It never allocates a replacement worker. The same authority fences prepared action recovery before its first dispatch; already claimed actions may still reconcile their original receipts without a live worker. Missing/expired workers defer fresh dispatch. For an existing real account with legacy NULL owner metadata, this authority calls the verified deterministic owner binder before checking the hold and lease. An absent or conflicting account is refused; enrollment itself grants no money or execution capacity. The owner check remains enforced.

Initial and recovered handlers hold a sixty-second companion lease, renewed every twenty seconds. A crash allows lease recovery after expiry; otherwise a retry waits thirty seconds. Discovery reads at most100 due companions, ordered by retry time and operation id. Unresolved valid records move their next attempt forward so they cannot permanently starve a later original. Provider and worker operation journals remain the effect fences after lease loss. The handler never gains authority to replay Lightning invoices, Cashu swaps, top-ups, publication, pre-admission starts or explicit checkpoint resumes through this poll.

The pinned ContextVM SDK0.13.10 cannot send a notification without an active in-memory client session after restart. Recovered notifications therefore cannot turn an authoritative result into an invalid-request error. The transport commits the original result and attempts delivery only through the SDK; a delivery failure during recovery leaves that cached reply available for the verified owner after reconnect/retry. It neither fabricates an SDK session nor falls back to unencrypted publication.

A committed response stays immutable. If its commit acknowledgement is lost, the transport reads and returns that exact original response. Once the response is committed, or the intake expires, the companion loses ciphertext, nonce and wrapped key; identity/digest/erasure metadata remain. Expiry preserves the original pending marker and does not prove that an uncertain financial operation was rejected. Public session status remains a separate read-only projection. The action-level encrypted archive has its own lifecycle, so erasing an intake after usage_unknown does not remove the command needed to settle an already prepared action.

The intake companion itself needs no new SQL migration or original-record rewrite. Verified account-owner enrollment has its own guarded migration proposal in [issue70](https://github.com/napplet/cvm/issues/70). Old pending records without companions remain explicit-command retry/query-only. Old binaries leave companions inert on rollback. Operator rollback, backup retention and disposal must retain a compatible cleanup process; logical expiry checks alone do not certify physical deletion from backups. These remain operational release gates.

Restricted PostgreSQL fixtures exercise paired rollback/lost acknowledgement, controller loss before the adapter/action, original response commit loss, concurrent recovery, tamper/owner/context/expiry denial, legacy cached replies, exclusion of payment tools and fairness beyond100 due records. The actual adapter/core/gateway/source/settlement composition recovers interrupted intake into one model POST and the original exact charge. Synthetic verified envelopes, local clocks and model/worker/rail protocol fixtures are explicit: these tests do not certify live Nostr delivery, provider retention, worker isolation or any protected release suite. An additional fixture constructs the actual pinned SDK without starting its relay, reproduces the missing-session notification failure and verifies that recovery caches the proper result. That is offline SDK behavior, not a signed reconnect or live delivery certificate. Existing signed-TLS integration checks remain required.

Fresh-price consent for changed/expired contexts, cancellation, the SQL-provider-claim/native-journal uncertainty window and complete worker lifetime/grace behavior remain separate requirements. This boundary does not license redispatch on uncertain acceptance.

Local implementation verification after owner enrollment: full transport 113/113 (2,765 assertions), pricing 89/89 (359 assertions), focused guarded intake/original-model composition 16/16 (623 assertions), wider persistence/ContextVM contracts 57/57 (331 assertions), catalog 17 tools, examples 3/3 and docs 56 pages/1,695 links. The pinned compiler still reports 430 repository errors; no changed source has a diagnostic. A pre-existing continuation test compared replay metadata as though both calls were original; it now verifies one original and one explicit replay with the identical durable claim, and runs in transport CI. No protected certification or deployment has been performed.
