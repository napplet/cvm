# Verified funding-account owners

[Schema proposal and technical compatibility review](https://github.com/napplet/cvm/issues/70) define this internal association. Public tool arguments, command fingerprints and money units are unchanged.

The production worker resolver needs a Nostr public key for its account. Previously, SQL account creation inserted only the account id and unit, leaving `nostr_pubkey` NULL. A model/worker-protocol fixture could pass while the actual resolver rejected that owner. The funding transaction now associates the verified principal with exactly `accountIdForPrincipal(pubkey)` before committing fresh credit or admission. Failed financial commands roll back enrollment with their other writes. A funding replay may idempotently enroll its own legacy NULL association without changing the original result or postings.

The SQL binder derives the account id itself. It cannot accept an arbitrary account id, replace a different non-NULL owner or recover a public key by guessing from its SHA256 account id. Fresh metered action preparation enrolls in its existing budget/action transaction; original-action recovery enrolls only after the retained command's full binding is checked. Neither association nor an audit row grants spending authority: signed principals, verified rail settlements, reservations and original operation identities still do that. The CVM receives no user private key.

Install `migrations/phase-07/008_production_account_owners.sql` before the new production funding runtime. The migration guards immutable non-NULL owners and their deterministic account hash, and records new associations in an append-only audit. Existing NULL rows are not bulk filled; existing non-NULL rows are not rewritten or retroactively claimed as newly verified. A conflicting legacy association remains intact and blocks production startup for evidence-based reconciliation. The async funding factory checks the installed owner guard/audit before opening the NWC connection.

During rollback, old writers may still insert NULL associations, but cannot reassign a bound owner. Preserve the audit and original account/ledger rows; do not drop them as a rollback step. The next verified owner command can enroll its legacy NULL account through the same binder. Account status remains read-only. The development/test and real-money schemas retain separate balances even for the same Nostr key.

The stronger SQL-backed worker check also exposed a receipt transition defect: a confirmed, priced receipt left its action in usage_unknown. Recording that validated receipt now returns the already claimed action to active/dispatching before building. Missing or unpriced usage stays unknown and never reaches a worker. This does not create another provider claim, operation, budget or charge. Original receipt recovery still uses lookup rather than another paid POST.

Restricted PostgreSQL tests cover legacy enrollment with unchanged ledger/result data, same-owner retries, conflicting/hash-mismatched owners, rollback and lost COMMIT acknowledgement, immutable audit/owner guards, separate test balances and restoration into a second local PostgreSQL container. The actual worker ownership resolver now participates in the model-composition fixture, including lost-response recovery. Pricing, model, worker and rail data in these tests are explicit fixtures; this is not live worker, funding or release certification evidence.
