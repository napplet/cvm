# Cloud Run resource profile and certification quantities

The native Google deployment request uses one project-owned profile for the control and Collector services:1 vCPU,512MiB memory,3 minimum/maximum instances, instance-based CPU allocation and no startup CPU boost. It sets the maximum at both service and revision levels. Mounted input cannot raise these fields. The returned service must match the declared profile before the original operation can become completed/owned; changed CPU, RAM, scaling mode, missing limits or added GPU limits remain unknown. The API's omitted false boolean representation is accepted only with the explicit matching resource limits.

The profile implements the [v2 service scaling](https://docs.cloud.google.com/run/docs/reference/rest/v2/projects.locations.services) and [container resource](https://docs.cloud.google.com/run/docs/reference/rest/v2/Container) contracts. It configures desired allocation, not a vendor-enforced currency cap, measured HA, accepted backlog result or readiness SLO. Actual provider behavior and costs still require protected evidence. Persistent background work requires the selected CPU-allocation policy; [instance-based billing](https://docs.cloud.google.com/run/docs/configuring/billing-settings) requires at least512MiB.

The same profile and existing15-minute authorization window produce2700 CPU-seconds and1350 GiB-seconds per planned region for each service family. Both control and Collector retain distinct europe-west1/us-central1 allocations. The previous Collector quantity covered only one instance despite using the same three-instance deploy path. The catalog now requires separate RAM facts and aggregates CPU/RAM into the existing16 authorization families. It cannot reuse a CPU quote for memory. The controller's request and cleanup durations retain their numerical values.

Google's [pricing table](https://cloud.google.com/run/pricing) treats vCPU-seconds and GiB-seconds separately. The catalog uses the API's shorthand usage-unit contract (`s`, `GiBy.s`) and requires a unique on-demand memory SKU offered in the selected region. Regional narrowing precedes semantic SKU uniqueness; discounted-only, absent, ambiguous or wrong-unit rows are refused. [Catalog schema](https://docs.cloud.google.com/billing/docs/reference/rest/v1/services.skus/list) distinguishes shorthand units from display descriptions. No memory SKU ID or rate is fabricated. Semantic selector availability and the actual selected account's prices remain unverified until an authenticated read succeeds. A public anonymous catalog request returned403; no credential or local profile was supplied/read, and no login was attempted. Fixture prices are test data and cannot certify the live catalog.

Existing journal intent hashes remain immutable. A legacy intent for different/unbounded service bytes is blocked before another network dispatch, never rewritten or automatically recreated. Original UID/createTime cleanup and uncertainty fences remain. New topology/source/cost quantities require a matching measured candidate and authorization; no old receipt gains these permissions.

This slice does not complete two-region mounted execution, SQL/GCS/network/registry/secret/report-query cost coverage, report-dispatch authority, the authenticated billing-evidence consumer or real certification. The optional Modal image remains unselected and its selector disabled. Private Beta and homelab deployment remain unchanged. No public or real-money traffic is enabled here.
